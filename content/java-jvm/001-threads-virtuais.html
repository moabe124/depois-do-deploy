Threads virtuais: libere a espera, controle a concorrência.

Objetivo: entender o que a JVM libera quando uma thread virtual espera por I/O e separar esse ganho do limite de chamadas simultâneas a uma API.

Intermediário · pré-requisito: threads e I/O13 de outubro de 2026Essencial · 3 minCompleta · 8 min + animação

Escolha o ritmo de hoje. O essencial explica o mecanismo, a decisão e o desafio.

01 / conceito

Uma thread pode esperar sem ocupar sua executora

Uma thread de plataforma corresponde a uma thread do sistema operacional. Uma thread virtual é gerenciada pela JVM e usa uma thread de plataforma para executar código. Essa executora recebe o nome de carrier.

Ao esperar por um I/O compatível, como uma operação de rede do JDK, a thread virtual pode ser desmontada da carrier. A tarefa continua pendente, mas a carrier fica disponível para outra tarefa. Quando o I/O termina, a JVM pode retomar a thread virtual em outra carrier. [1]

Isso permite manter muitas tarefas concorrentes com código sequencial. Concorrência é ter tarefas em andamento; paralelismo é executar mais de uma ao mesmo tempo. A quantidade de núcleos ainda limita o trabalho de CPU. [2]

Threads virtuais são estáveis desde o Java 21. A proposta é ampliar a capacidade de lidar com espera; uma chamada lenta não passa a terminar mais rápido só por trocar de thread. [2]

02 / problema

A fila sumiu do pool. Para onde ela foi?

Um serviço consulta uma API de cotações. Cada requisição faz pouco cálculo e espera pela rede. Um pool de 20 threads de plataforma deixa apenas 20 tarefas executando por vez; as demais ficam na fila do executor.

A equipe troca o pool por Executors.newVirtualThreadPerTaskExecutor(). Esse executor cria uma thread virtual por tarefa e não impõe um limite de threads. [3]

Agora o serviço consegue iniciar muito mais consultas. Porém, no nosso cenário hipotético, a API só tolera 20 chamadas simultâneas por instância cliente. A troca pode aumentar a pressão sobre a dependência e provocar mais timeouts. Ter carriers disponíveis não significa que a API tenha capacidade disponível.

03 / solução

Separe execução de permissão para chamar

Use uma thread virtual por tarefa e um semáforo compartilhado na fronteira da API. Cada chamada precisa obter uma permissão; ao terminar, devolve essa permissão. Não crie um pool de threads virtuais para representar a capacidade da dependência. [2]

No exemplo, há 20 permissões. Se todas estiverem ocupadas, a tarefa espera no máximo 100 ms para entrar. Sem vaga nesse prazo, o serviço retorna uma falha controlada. Esse tempo e o limite 20 são escolhas didáticas, a validar com medição. [4]

Uma chamada que já entrou mantém a permissão enquanto espera pela API. Ela pode liberar sua carrier durante o I/O e ainda ocupar uma permissão: são recursos diferentes. A permissão só volta quando a operação termina ou falha.

O semáforo limita chamadas em andamento, não requisições por segundo. Também não limita sozinho quantas tarefas aguardam por uma vaga. Combine-o com controle de admissão, espera limitada e timeout de I/O.

Libere a thread que executa. Preserve o limite do recurso que espera.

04 / aprofundamento opcional

Como levar o mecanismo para o código

BaseO que muda quando o trabalho usa CPU?

Comprimir um arquivo ou processar uma imagem pode ocupar a CPU por muito tempo. Nessa fase, a thread virtual precisa continuar executando em uma carrier. Criar milhares delas não cria milhares de núcleos. [1]

Se CPU é o gargalo, meça a demanda e controle o paralelismo do trabalho pesado. A vantagem das threads virtuais aparece principalmente quando há muitas tarefas com períodos de espera por I/O.

O mesmo cuidado vale para memória. Tarefas suspensas continuam mantendo estado, objetos e contexto de execução. Um grande número de threads virtuais pode consumir heap relevante.

AplicaçãoAdquirir, chamar e devolver — inclusive na falha

O trecho abaixo pertence a uma instância compartilhada de cliente da API. chamada é uma operação síncrona com seus próprios timeouts de conexão e resposta. O método é chamado de dentro de uma thread virtual.

private final Semaphore vagasApi = new Semaphore(20);

public <T> T consultar(Callable<T> chamada) throws Exception {
    if (!vagasApi.tryAcquire(100, TimeUnit.MILLISECONDS)) {
        throw new TimeoutException("API sem vaga no prazo");
    }
    try {
        return chamada.call();
    } finally {
        vagasApi.release();
    }
}

Importe Callable, Semaphore, TimeUnit e TimeoutException de java.util.concurrent. O finally só é alcançado depois da aquisição bem-sucedida. Assim, uma falha antes de obter vaga não inventa uma permissão; uma falha da chamada devolve a vaga.

Se a aquisição for interrompida, o método propaga InterruptedException. Quem capturar essa exceção deve respeitar o cancelamento; não continuar a operação como se tivesse adquirido uma vaga. [4]

try (var tarefas = Executors.newVirtualThreadPerTaskExecutor()) {
    var resultado = tarefas.submit(() ->
        clienteCompartilhado.consultar(() -> buscarCotacao()));
    System.out.println(resultado.get());
}

Esse segundo trecho demonstra um lote finito. Em um servidor, gerencie o executor no ciclo de vida da aplicação. A saída do try aguarda a conclusão das tarefas: fechar o executor não cria um deadline. [5]

No HTTP Client do JDK, HttpRequest.Builder.timeout(...) limita a espera pela resposta da requisição. O timeout de conexão é configurado no cliente. Confira as garantias da biblioteca que seu serviço usa. [6]

Se chegarem tarefas mais rápido do que terminam, elas ainda podem se acumular antes do semáforo. Controle a admissão na entrada do serviço e monitore tarefas pendentes, espera, recusas, duração das chamadas e uso de memória.

Dez instâncias com 20 permissões cada podem manter até 200 chamadas em andamento. Um contrato global de 20 não é protegido por dez semáforos locais. Distribua o orçamento ou use um controle coordenado. Evite criar um semáforo novo por requisição.

ProfundidadePinning: a versão da JVM muda o diagnóstico

Pinning ocorre quando uma thread virtual não consegue se desmontar da carrier durante uma operação bloqueante. Esse período reduz a capacidade de reutilizar a executora. [1]

No JDK 21, bloquear enquanto mantém um monitor de synchronized pode causar pinning. O JDK 24 removeu o pinning associado a esses monitores. Por isso, uma recomendação de migração escrita para Java 21 não deve ser aplicada automaticamente a uma JVM mais nova. [7]

Chamadas nativas e funções estrangeiras ainda merecem investigação. Além disso, evitar pinning não remove exclusão mútua: uma seção crítica longa continua serializando acesso. Investigue o caminho real de I/O e a versão do driver antes de atribuir o gargalo ao scheduler.

JDK Flight Recorder permite observar eventos como jdk.VirtualThreadPinned. Use os eventos disponíveis na sua versão e combine-os com latência, throughput e saturação da dependência. [1]

05 / desafio

O que você protegeria primeiro?

Três camadas para estudo. As respostas começam escondidas; o desafio não diagnostica seu nível profissional.

Base — A aguarda a resposta da API

A liberou sua carrier, mas ainda mantém uma permissão. Isso é possível?

Ver resposta da base

Sim. A carrier executa código; a permissão representa uma chamada ainda em andamento. A deve manter a permissão enquanto espera pela API.

Aplicação — O executor deixou de limitar a concorrência

Mil tarefas consultam uma API com orçamento local de 20 chamadas simultâneas. Qual decisão atende a esse limite?

Ver resposta da aplicação

Compartilhe o semáforo. Toda chamada dessa instância deve atravessar o mesmo controle. Um semáforo por requisição não mantém o limite agregado. Limite também admissão e duração da operação.

Profundidade — A frota cresceu

Há cinco instâncias, cada uma com 20 permissões. A API impõe limite global de 20. O limite está protegido?

Ver resposta da profundidade

O limite local não protege o contrato global. Cinco vezes 20 permite até 100 chamadas. Fairness altera a ordem de aquisição local, não coordena instâncias.

A espera ficou mais barata. A capacidade da dependência continua finita.
