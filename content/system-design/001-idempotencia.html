01 / o conceito

Idempotência: repetir sem duplicar.

Idempotência é poder repetir uma operação sem gerar efeitos adicionais. Aqui, queremos que várias tentativas de pagar o pedido correspondam a uma única cobrança.

Pense em uma comanda: perguntar três vezes pela comanda 2048 não cria três pedidos. A chave de idempotência funciona como esse identificador. Ela nasce para uma intenção de pagamento e acompanha todas as tentativas dessa intenção.

Não use apenas o valor ou o conteúdo da requisição para identificar duplicatas. Duas compras legítimas podem ser iguais. Também não gere uma chave nova a cada retry: você estaria dando um novo nome à mesma intenção.

Retry: uma nova tentativa de executar a mesma operação.

Timeout: o prazo de espera pela resposta acabou. O resultado ainda pode ser desconhecido.

Reconciliação: verificar o resultado no provedor e atualizar o estado local.

02 / o problema

Uma cobrança. Duas tentativas.

São 18h47. Você só queria um café. Toca em “pagar”. A tela gira por alguns segundos e avisa: algo deu errado, tente novamente. Você tenta. Dois minutos depois, chegam duas notificações do banco.

Do outro lado, a primeira cobrança tinha funcionado. Foi a resposta que se perdeu no caminho. O retry foi tratado como uma operação nova. A segunda tentativa virou uma segunda cobrança.

O aplicativo diz“Não recebi a confirmação.”

O servidor diz“Eu processei o pagamento.”

A pergunta de arquitetura“Como repetir a tentativa sem repetir o efeito?”

03 / como o conceito resolve

Reconhecer. Reservar. Reconciliar.

Para o nosso café, começamos com uma API, um banco relacional e um provedor que aceita operações idempotentes. O requisito de negócio é claro: uma intenção de pagamento não pode cobrar duas vezes.

  1. Reconhecer a intenção.O cliente envia a mesma chave nas repetições. A API associa a chave ao cliente autenticado e confere se pedido, valor e moeda continuam iguais.
  2. Reservar a operação, de forma atômica.Uma restrição única no banco impede que duas chamadas concorrentes criem a mesma operação. O registro começa como “em processamento”.
  3. Chamar o provedor com uma chave estável.Se a chamada precisar ser repetida, o provedor deve reconhecer a intenção original. Ao confirmar, registramos o resultado.
  4. Reconciliar quando falta certeza.Se houve timeout ou queda da API, consultamos ou repetimos com segurança no provedor. Até esclarecer, a interface mostra “confirmando pagamento”.

O cenário com chave pressupõe que API e provedor reconhecem a mesma operação, dentro do prazo de retenção. Nenhuma cobrança real é executada.

cliente + chave → identificação única pedido + valor + moeda → intenção conferida estado → em processamento | concluída | falha confirmada referência do provedor → caminho para reconciliação

Um registro pendente não pode ficar esquecido. Ele precisa de um responsável, prazo de investigação e rotina de recuperação. Tempo decorrido, sozinho, não prova que a cobrança falhou.

04 / por baixo do balcão

O detalhe que muda o projeto.

Uma chave no seu banco não cria uma transação com o provedor. Existem duas fronteiras de confirmação. É nesse intervalo que o raciocínio de especialista aparece.

Base · sem pressaPor que desabilitar o botão não resolve?

Desabilitar o botão melhora a experiência. Mas o aplicativo pode repetir a requisição após um erro, o usuário pode recarregar a página e duas abas podem enviar o pedido. A garantia precisa existir no servidor, independentemente da interface.

Intermediário · concorrênciaE se duas tentativas chegarem juntas?

“Consultar e depois inserir” abre uma condição de corrida: ambas podem consultar antes de qualquer inserção. Use a restrição única para decidir quem reserva a operação. Quem perde a reserva consulta o registro existente e devolve o resultado, ou um estado de processamento.

Uma resposta como 202 Accepted pode expressar processamento em andamento, se esse for o contrato da API. Ela precisa vir com um caminho para consultar o status. O código HTTP sozinho não resolve o fluxo.

Avançado · falha parcialO provedor cobrou. A API caiu antes de salvar.

O registro local continua pendente, embora o dinheiro já tenha saído. Criar uma nova operação nesse momento pode duplicar a cobrança. Um processo de recuperação usa a referência estável para consultar o provedor ou repetir a chamada com a mesma chave, conforme o contrato dele.

A escrita local e a chamada externa não são atômicas. Uma transação no banco resolve a reserva local; ela não desfaz uma cobrança externa. Se o provedor não oferecer deduplicação nem consulta confiável, a garantia fica mais fraca e pode exigir revisão manual.

Uma fila ou um outbox ajuda a retomar trabalho após falhas, mas também pode entregar mais de uma vez. O efeito externo ainda precisa de idempotência.

Avançado · limites da garantiaPor quanto tempo uma repetição é reconhecida?

Guardar chaves para sempre tem custo. Apagá-las cedo demais permite que um retry tardio pareça uma nova operação. Defina a retenção com base na janela real de repetição e no contrato do provedor; mantenha também uma regra de negócio durável para o pedido já pago.

Na Stripe, os registros podem ser removidos depois de pelo menos 24 horas. Ela também pode devolver o mesmo resultado de erro salvo para uma chave. Isso é um contrato específico, não uma regra universal para toda API idempotente. Consultar o contrato da Stripe ↗

Em múltiplas regiões, dois bancos locais com restrição única não garantem unicidade global. Você precisa definir onde a intenção é coordenada e como o sistema se comporta durante uma partição de rede.

O que você defenderia numa revisão?

  • A garantia: uma cobrança por intenção, nas condições descritas.
  • O custo: estado persistente, recuperação e uma experiência com processamento pendente.
  • A operação: medir idade dos pendentes, divergências e falhas de reconciliação; alertar antes de afetarem clientes.

O salto para especialista inclui tornar as garantias, os limites e a recuperação compreensíveis para o time.
