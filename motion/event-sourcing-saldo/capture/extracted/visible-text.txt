System Design / conceito Event sourcing: guarde os fatos, derive o estado. Objetivo: entender o que é event sourcing: guardar cada mudança como um evento imutável, calcular o estado atual a partir desses eventos e criar projeções para leitura, reconhecendo quando o padrão compensa e quando é custo desnecessário. A animação tem controles nativos e uma imagem estática. 01 / conceito O banco guarda o resultado. O event sourcing guarda o que aconteceu. No modelo mais comum, o CRUD , a tabela guarda o estado atual : o último valor de cada campo. Quando algo muda, um UPDATE troca o valor antigo pelo novo. É simples e rápido para a maioria dos casos. [1] Event sourcing muda o que é guardado. Cada mudança vira um evento : o registro de algo que já aconteceu, como “pontos creditados” ou “pontos resgatados”. Os eventos vão para um armazenamento de eventos ( event store ) em que só se acrescenta no fim ( append-only ). Nenhum evento é alterado ou apagado. O estado atual vira consequência: é o resultado de aplicar os eventos, em ordem. [2] Você já conhece essa ideia. Um extrato bancário não trata “saldo = 300” como a verdade. Ele guarda os lançamentos, e o saldo é a soma deles. O Git funciona parecido: o histórico de commits é o registro de eventos, e a cópia de trabalho é o estado. [3] O saldo é consequência. O evento é o fato. 02 / problema “Eu tinha 1.200 pontos. Cadê?” Um app de varejo tem um programa de pontos. Cada cliente tem uma carteira, e a tabela carteiras guarda uma coluna saldo . Toda compra, resgate ou expiração faz um UPDATE nessa coluna. Um cliente abre um chamado: “Semana passada eu tinha 1.200 pontos. Hoje tenho 300. O que aconteceu?” O suporte consulta o banco e encontra só o número 300. O valor anterior foi sobrescrito, e a explicação se perdeu com ele. A equipe já tinha tentado resolver isso com uma tabela de histórico, gravada pelo código logo depois de cada UPDATE . Mas o job noturno de expiração foi escrito depois e não grava no histórico. Agora existem duas versões da verdade , o saldo e o histórico, e elas discordam. O que o negócio precisa: explicar qualquer saldo, corrigir um erro sem apagar o que aconteceu e responder a perguntas novas sobre o passado, como “quantos pontos expiraram por mês desde o lançamento?”. 03 / solução Anexar o fato, calcular o saldo Com event sourcing, cada carteira tem seu fluxo de eventos ( stream ): a lista ordenada de tudo o que aconteceu com ela. A carteira 42 fica assim: Fluxo de eventos da carteira 42 # Evento Pontos Detalhe 1 PontosCreditados +1.000 compra 7781 2 PontosCreditados +200 compra 7802 3 PontosResgatados −400 vale-presente 4 PontosExpirados −500 lote de março O saldo sai da aplicação dos eventos em ordem: 1.000 + 200 − 400 − 500 = 300 . Agora o suporte responde com fatos: 400 pontos viraram um vale-presente e 500 expiraram. Não existe uma segunda tabela para alguém esquecer de atualizar. O histórico é o dado. Cada mudança passa por três peças, e vale separar bem os nomes: Comando: um pedido, que pode ser recusado. “Resgatar 400 pontos” é um comando. Para decidir, o sistema lê os eventos da carteira, calcula o saldo e aplica a regra: há pontos suficientes? [3] Evento: se a regra permitir, o sistema anexa um fato ao fim do fluxo, como PontosResgatados . O nome fica no passado porque o fato já aconteceu. [1] Projeção: ler e somar todos os eventos a cada consulta sai caro. Por isso o sistema mantém projeções (ou read models ): visões derivadas dos eventos e prontas para leitura, como a tabela de saldos ou o extrato da tela. [1] Consulte a imagem estática e a descrição abaixo. Do número sobrescrito ao histórico que se explica. Na tabela comum, o resgate e a expiração trocam o saldo de 1.200 para 800 e depois para 300, e o motivo se perde. Com event sourcing, quatro eventos são anexados em ordem e o saldo é calculado a partir deles. No fim, a expiração indevida é corrigida por um quinto evento, sem alterar o evento 4. Hipóteses: programa de pontos e valores fictícios; a projeção aparece atualizada logo após cada evento, embora em muitos sistemas ela seja atualizada com algum atraso. Reproduzir Repetir do início Velocidade 0,5× 1× 1,5× 2× 24 segundos · reprodução manual · uma passagem por vez. Ver a explicação estática Em código, a ideia central cabe em duas funções. Os nomes são ilustrativos: // Estado atual = eventos aplicados em ordem function calcularSaldo(eventos) { return eventos.reduce((saldo, evento) => { switch (evento.tipo) { case 'PontosCreditados': return saldo + evento.pontos; case 'PontosResgatados': return saldo - evento.pontos; case 'PontosExpirados': return saldo - evento.pontos; case 'ExpiracaoEstornada': return saldo + evento.pontos; default: return saldo; } }, 0); } // Comando: decide com base nos fatos e anexa um fato novo async function resgatar(carteiraId, pontos) { const { eventos, versao } = await eventStore.ler(carteiraId); if (calcularSaldo(eventos) < pontos) throw new Error('Saldo insuficiente'); await eventStore.anexar(carteiraId, [{ tipo: 'PontosResgatados', pontos }], { versaoEsperada: versao }); } Nenhuma linha faz UPDATE . O comando só lê e anexa. O parâmetro versaoEsperada protege contra dois resgates simultâneos; ele aparece no aprofundamento. Errou? Registre a correção A expiração do evento 4 foi indevida: o lote de março ainda valia. Num sistema CRUD, alguém corrigiria o número na tabela. Com event sourcing, não se edita o passado . O sistema anexa um evento compensatório , que desfaz o efeito do anterior: ExpiracaoEstornada +500 , o evento 5. O saldo volta para 800, e o histórico mostra o erro e a correção. [1] O passado não se edita. A correção é um fato novo. O que se ganha e o que se paga Como os eventos guardam o que aconteceu, dá para reconstruir qualquer projeção do zero, consultar o estado em uma data passada e criar visões que ninguém tinha previsto. [2] A pergunta do marketing, pontos expirados por mês, vira uma projeção nova, processada desde o primeiro evento. O custo também existe. A Microsoft descreve event sourcing como um padrão complexo, caro de adotar e de abandonar, e lembra que, na maioria dos sistemas, o armazenamento tradicional basta. [1] 04 / aprofundamento opcional Os detalhes que aparecem em produção Base Event sourcing não é o mesmo que mensageria “Orientado a eventos” virou um termo amplo. Martin Fowler separa quatro padrões: notificação de evento (avisar outros sistemas de que algo mudou), transferência de estado por evento (o evento leva os dados para o consumidor guardar uma cópia), event sourcing (o log de eventos é a fonte da verdade do estado) e CQRS (modelos separados para escrita e leitura). [3] Usar Kafka não torna um sistema event sourced. A Microsoft alerta para não confundir o armazenamento de eventos com um broker de mensagens: brokers como o Kafka em geral não oferecem leitura do fluxo de uma entidade nem concorrência otimista. Eles servem bem para distribuir eventos a projeções e a outros sistemas, mas não substituem o armazenamento de eventos. [1] Event sourcing e CQRS aparecem juntos com frequência, mas são independentes. As projeções fazem o papel do lado de leitura. Fowler recomenda cautela com CQRS: na maioria dos sistemas, um modelo CRUD é mais adequado. [4] Aplicação A projeção pode atrasar Em muitas implementações, o evento é gravado primeiro e as projeções são atualizadas logo depois, por outro processo. Nesse intervalo, a tela de saldo ainda mostra o valor antigo. Isso é consistência eventual : a projeção alcança os eventos, mas não no mesmo instante. [1] Na prática, o comando de resgate pode devolver o novo saldo na própria resposta, em vez de reler a projeção, ou a tela pode mostrar “processando” até a projeção alcançar. A regra de negócio (há saldo?) é decidida com os eventos, não com a projeção. A entrega de eventos aos consumidores costuma ser pelo menos uma vez . Por isso a projeção precisa ser idempotente : processar o mesmo evento duas vezes não pode descontar os pontos duas vezes. Uma técnica comum é guardar o número do último evento processado e ignorar os repetidos. [1] A edição sobre idempotência e retries seguros aprofunda essa ideia. Aplicação Dois resgates ao mesmo tempo A carteira tem 500 pontos, e dois pedidos de resgate de 400 chegam juntos. Os dois leem os eventos na versão 4 , calculam saldo 500 e aprovam. Se os dois gravassem, o saldo ficaria em −300. O armazenamento de eventos evita isso com concorrência otimista . Cada gravação informa a versão que leu ( versaoEsperada: 4 ). A primeira grava o evento 5. A segunda é rejeitada, porque o fluxo já não está na versão 4. Ela relê os eventos, recalcula o saldo, agora 100, e recusa o resgate. [1] [5] Essa proteção vale dentro de um fluxo. Regras que envolvem várias entidades, como estoque e pedido, precisam de outra estratégia, como avisar o cliente ou abrir uma pendência. [1] Profundidade Fluxos longos, eventos que mudam e dados pessoais Snapshots: uma carteira com anos de eventos fica lenta para recalcular. Um snapshot guarda o estado em um ponto do fluxo, por exemplo a cada N eventos. Para recalcular, carrega-se o snapshot e aplicam-se só os eventos posteriores. O snapshot é uma otimização; os eventos continuam sendo a fonte da verdade. [1] Versionamento: eventos antigos ficam para sempre, então o formato deles precisa evoluir com cuidado. Estratégias comuns: leitores que toleram campos novos, versão no tipo do evento e upcasting , que converte eventos antigos para o formato atual na leitura, sem reescrevê-los. Um bug que gravou eventos errados também fica no histórico: corrigir o código não corrige o passado, que pede eventos compensatórios. [1] Replay e sistemas externos: ao reprocessar eventos para reconstruir uma projeção, o sistema não pode reenviar e-mails nem repetir cobranças. Fowler sugere isolar essas chamadas atrás de um gateway desligado durante o replay. [2] Dados pessoais: um log imutável conflita com leis de proteção de dados que exigem apagar dados pessoais. Duas saídas comuns: manter os dados pessoais fora dos eventos, referenciados por um identificador, ou criptografá-los com uma chave por pessoa e apagar a chave quando necessário ( crypto-shredding ). Base — Um resgate lançado por engano Um atendente lançou por engano um resgate de 400 pontos na carteira de um cliente. O sistema usa event sourcing. Qual é a correção certa? Editar o evento de resgate para 0 pontos. Anexar um evento que devolve os 400 pontos, como ResgateEstornado . Apagar o evento de resgate e recalcular o saldo. Ver resposta da base Anexe um evento compensatório. O resgate errado continua no histórico, e o estorno registra a correção. O saldo volta ao valor certo, e a auditoria mostra o que aconteceu. Aplicação — Uma pergunta que ninguém previu Dois anos depois do lançamento, o marketing quer saber quantos pontos expiraram em cada mês. Nenhuma tela ou tabela registra isso, mas todos os eventos estão guardados desde o início. O que fazer? Criar uma projeção nova e processá-la desde o primeiro evento. Começar a contar a partir de hoje; o passado não foi medido. Adicionar uma coluna à tabela de saldos e preenchê-la com o saldo atual. Ver resposta da aplicação Crie uma projeção nova. Os eventos PontosExpirados já registram quanto e quando expirou. A projeção lê os fluxos desde o início e monta o relatório, inclusive para os meses passados. Profundidade — Dois resgates ao mesmo tempo Uma carteira tem 500 pontos, e dois resgates de 400 chegam juntos. Os dois leram a carteira na versão 4. O que impede o saldo de ficar negativo? A gravação com versão esperada: o segundo resgate é rejeitado, relê os eventos e é recusado por falta de saldo. Consultar a projeção de saldo logo antes de gravar. Nada: os dois eventos são anexados e a projeção corrige o saldo depois. Ver resposta da profundidade A versão esperada. O armazenamento de eventos só aceita a gravação se o fluxo ainda estiver na versão lida. A projeção não protege: ela pode estar atrasada e não participa da gravação. Anexar os dois deixaria o saldo em −300, um fato que depois exigiria compensação. [5] Tabelas contam onde você está. Eventos contam como você chegou até aí.
