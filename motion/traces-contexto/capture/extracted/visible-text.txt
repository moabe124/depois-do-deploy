Objetivo: diagnosticar onde uma requisição gasta tempo entre serviços e filas, preservando a propagação do cabeçalho W3C traceparent , escolhendo entre hierarquia pai-filho e span links e reconhecendo o impacto da amostragem. A animação tem controles nativos e uma imagem estática. 01 / conceito Um trace é uma árvore de trechos unidos por contexto Um trace representa o caminho completo de uma operação enquanto ela atravessa processos, redes e filas. A sua unidade básica é o span : um trecho nomeado e cronometrado de trabalho, com instante de início, duração, código de status e metadados. [1] Para que trechos gravados em máquinas diferentes formem a mesma árvore, cada operação carrega um Span Context imutável. O primeiro trecho sem pai é o span raiz ; os demais apontam para quem os acionou por meio de um parent_id ou de uma associação causal. [1] Quando a execução cruza a fronteira de um processo, entra a propagação de contexto : serializar esse estado na saída ( injeção ) e reconstruí-lo na entrada ( extração ). O padrão W3C Trace Context define o cabeçalho traceparent para transportar a identidade da operação de forma interoperável: [2] [3] traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 │ │ │ └── trace-flags (01 = sampled) │ │ └── parent-id (16 hex · span do chamador) │ └── trace-id (32 hex · identidade global do trace) └── version (00) Em cada salto entre serviços, o trace-id permanece idêntico para manter o rastro unido. Já o parent-id precisa ser atualizado com o identificador do span que realizou a chamada de saída. [2] 02 / problema O cliente esperou 1.800 ms, mas cada serviço jura que foi rápido Após um deploy, o fechamento de compra ( POST /pedidos ) passa a levar 1.800 ms nos percentis mais altos. O fluxo cruza três serviços: o BFF recebe a chamada do aplicativo, aciona a API de Pedidos via HTTP e aguarda a confirmação da reserva processada pelo Worker de Estoque através de uma fila. Nas métricas individuais, a API de Pedidos responde em 140 ms e o Worker de Estoque processa cada reserva em 400 ms . Quando a equipe abre o coletor de traces para investigar um pedido lento, encontra dois rastros separados: um termina na publicação da fila e outro nasce no worker com um trace-id diferente. A quebra aconteceu na fronteira assíncrona. O produtor publicou o JSON da reserva, mas não injetou traceparent nos cabeçalhos da mensagem. Sem contexto recebido, o consumidor iniciou um novo span raiz . Os 1.260 ms em que a mensagem ficou parada na fila desapareceram entre dois traces órfãos. 03 / solução Propague na fronteira e leia a cascata A investigação deixa de ser adivinhação quando todos os saltos preservam o contexto. Em chamadas HTTP, bibliotecas instrumentadas costumam repassar traceparent ; em filas, wrappers próprios ou jobs agendados, confirme que o produtor injeta o contexto nos metadados da mensagem e que o consumidor o extrai antes de abrir seu span. [3] [4] Com o mesmo trace-id (abreviado aqui como 4bf9 ), a visualização em cascata ( waterfall ) alinha os trechos no tempo. No nosso cenário didático: o span a1 no BFF permanece aberto por 1.800 ms ; os spans b2 e c3 na API de Pedidos somam 140 ms ; e o span d4 no Worker de Estoque só começa em 1.400 ms , durando 400 ms . O espaço vazio entre o fim de c3 (em 140 ms) e o início de d4 (em 1.400 ms) revela 1.260 ms sem nenhum código executando . O problema não era banco lento nem CPU saturada no worker: era atraso de fila (backlog) por falta de consumidores suficientes para a vazão do horário de pico. Consulte a imagem estática e a descrição abaixo. Do rastro partido à cascata completa. Sem traceparent na fila, o consumidor abre outro trace ( 9c10 ) e esconde o tempo de espera. Com inject e extract de traceparent: 00-4bf9-c3-01 , o worker cria span d4 ligado a c3 no mesmo trace 4bf9 , expondo os 1.260 ms de fila. Hipóteses: IDs abreviados para leitura, relógios sincronizados entre serviços, uma mensagem por pedido. A duração visual da animação não está na escala dos milissegundos. [3] O trace só atravessa a fronteira quando o contexto viaja junto com a chamada. 04 / aprofundamento opcional Garantias do protocolo, mensageria e amostragem Base O que cada campo do W3C Trace Context garante? A recomendação W3C Trace Context divide a propagação em dois cabeçalhos: traceparent (identidade e posição no grafo, em formato fixo para leitura rápida) e tracestate (lista opcional de pares chave=valor separados por vírgula para metadados específicos de fornecedores ou coletores). [2] Na versão 00 de traceparent , trace-id tem 32 caracteres hexadecimais minúsculos (16 bytes) e parent-id tem 16 caracteres hexadecimais minúsculos (8 bytes). Valores compostos apenas por zeros são inválidos: se trace-id ou parent-id forem inválidos, o serviço receptor deve ignorar o cabeçalho e iniciar um novo trace. [2] Já uma falha ao interpretar tracestate não pode invalidar um traceparent válido. E ao interpretar trace-flags , use máscara de bits ( flags &amp; 0x01 ) em vez de comparar o byte inteiro com 01 , preservando compatibilidade com outros bits. [2] Aplicação Injetar e extrair contexto nos cabeçalhos da fila Quando o cliente de mensageria não propaga o contexto automaticamente, use a Propagators API do OpenTelemetry. O propagador não conhece o protocolo de transporte: ele lê e escreve em um portador ( carrier ), como o mapa de cabeçalhos da mensagem. [4] import { context, propagation, trace, SpanKind } from '@opentelemetry/api'; const tracer = trace.getTracer('pedidos'); // Produtor: cria o span de envio e injeta o contexto nos headers da mensagem export async function publicarReserva( broker, payload ) { const headers = {}; return tracer.startActiveSpan('send estoque.reservas', { kind: SpanKind.PRODUCER }, async span =&gt; { try { propagation.inject(context.active(), headers); await broker.publish('estoque.reservas', payload, { headers }); } finally { span.end(); } }); } // Consumidor: extrai o contexto recebido e vincula o span de processamento export async function consumirReserva( mensagem, processar ) { const ctxRemoto = propagation.extract(context.active(), mensagem.headers ?? {}); const spanRemoto = trace.getSpanContext(ctxRemoto); const links = spanRemoto ? [{ context: spanRemoto }] : []; return tracer.startActiveSpan('process estoque.reservas', { kind: SpanKind.CONSUMER, links }, async span =&gt; { try { return await processar(mensagem.payload); } finally { span.end(); } }); } Repare na fronteira de segurança: serviços expostos diretamente à internet pública não devem confiar cegamente em cabeçalhos de trace vindos de clientes não confiáveis sem validação ou política de borda, e dados sensíveis, tokens ou informações pessoais nunca devem ser colocados em tracestate ou baggage . [2] [3] Aplicação Pai-filho ou Span Link? A escolha certa para filas e lotes No modelo do OpenTelemetry, cada span pode ter apenas um parent_id , mas pode registrar múltiplos Span Links apontando para outros contextos. Essa diferença é decisiva em mensageria. [5] Como relacionar produtor e consumidor Relação Quando usar Compromisso parent_id direto Chamadas síncronas (HTTP/gRPC) ou cenários de mensagem única sem outro contexto ativo Une tudo na mesma cascata, mas não representa um lote com vários produtores nem preserva outro contexto ambiente Span Link Consumo em lote ( batch ), fan-in ou handlers acionados dentro de um contexto HTTP do broker Preserva a causalidade exata com um ou dezenas de produtores sem fingir um único pai As convenções semânticas do OpenTelemetry para mensageria — atualmente em estágio de desenvolvimento ( Development ), enquanto a API de Traces e o W3C Trace Context são estáveis — adotam Span Links como padrão para ligar o span process ao contexto de criação de cada mensagem. Apenas em processamento de mensagem única sem contexto ambiente o uso de parent_id direto aparece como opção configurável. [6] Além disso, os relógios de máquinas diferentes sofrem desvio ( clock skew ). Uma diferença de dezenas de milissegundos via NTP pode fazer um span filho parecer começar ligeiramente antes do pai na linha do tempo. Valide a causalidade pelo parent_id e pelos links, não apenas pela posição absoluta do timestamp. Profundidade Head sampling vs. Tail sampling: por que o trace do incidente sumiu? Em sistemas com milhares de requisições por segundo, exportar 100% dos traces pode custar caro. A flag sampled ( 01 ) do traceparent foi desenhada para o head sampling : o primeiro serviço decide logo na entrada (por exemplo, reter 5% das requisições de forma determinística pelo trace-id ) e todos os serviços seguintes respeitam essa decisão. [2] [7] O ganho do head sampling é eficiência e completude : se um trace é amostrado, todos os seus spans são exportados. O limite é que, no início da requisição, o sistema ainda não sabe se o último serviço vai lançar um erro ou se a fila vai demorar 1.260 ms. [7] Se um serviço intermediário tentar resolver isso sozinho ligando o bit sampled apenas daquele ponto em diante após detectar um erro, você terá um trace incompleto : os spans iniciais no BFF e na API já foram descartados. Para reter 100% dos traces com erro ou alta latência sem gravar todo o tráfego saudável, usa-se tail sampling em uma camada coletora (como o Tail Sampling Processor do OpenTelemetry Collector). As aplicações exportam os spans candidatos para o coletor, que mantém o trace em buffer por uma janela de tempo e decide ao final se armazena ou descarta o conjunto inteiro. [7] O custo operacional do tail sampling: o coletor deixa de ser apátrida ( stateless ). Todos os spans de um mesmo trace_id precisam chegar à mesma instância do coletor (balanceamento por trace_id ), o consumo de memória cresce com a duração dos traces e é preciso monitorar o próprio coletor para evitar descarte sob pico de carga. [7] 05 / desafio Como você preservaria a evidência? Três camadas para estudo. As respostas começam escondidas; o desafio não diagnostica seu nível profissional. Base — O que muda no traceparent ao chamar o próximo serviço? O BFF recebeu um trace com trace-id = 4bf9... e executa o span a1 . Ao chamar a API de Pedidos criando o span de saída b2 , o que o cabeçalho traceparent enviado deve conter? O mesmo trace-id (4bf9...) e o parent-id atualizado para o span que faz a chamada (b2). Um novo trace-id para a API de Pedidos e o parent-id mantendo o span raiz (a1). Exatamente a mesma string traceparent recebida na entrada, sem alterar nenhum campo. Ver resposta da base Mantenha o trace-id e atualize o parent-id . O trace-id identifica a árvore inteira; o parent-id informa ao destinatário qual span imediato originou aquela chamada. Aplicação — Um consumidor processa 50 mensagens de uma vez Um worker lê um lote de 50 mensagens da fila e faz um único INSERT em lote no banco. Cada mensagem veio de uma compra diferente, com seu próprio trace-id . Como instrumentar o span de processamento do lote? Usar o traceparent da primeira mensagem como parent_id e ignorar o contexto das outras 49. Extrair o contexto de cada mensagem e adicioná-los como Span Links no span do lote. Descartar todos os cabeçalhos porque um span não pode se conectar a múltiplos traces. Ver resposta da aplicação Use Span Links para cada mensagem do lote. Um span só aceita um único parent_id , mas pode ter links para todos os contextos de criação que compõem aquele lote, preservando a rastreabilidade das 50 compras. Profundidade — Capturar 100% dos traces lentos sem gravar tudo Com head sampling probabilístico de 1% na borda, 99% dos pedidos lentos ou com erro no último serviço não são gravados. Qual arquitetura resolve esse requisito mantendo traces completos? Trocar a semente aleatória do head sampler apenas no último serviço. Adotar tail sampling no coletor, roteando spans pelo trace-id para decidir após o término. Mudar a flag sampled para 01 somente no worker quando a execução passar de 1 segundo. Ver resposta da profundidade Use tail sampling com roteamento por trace-id . Mudar a flag apenas no último serviço não recupera os spans anteriores que o BFF e a API já deixaram de gravar. O coletor precisa reunir os spans do trace antes de decidir retê-lo. Logs contam o que aconteceu em um nó. O contexto propagado conta por que aquilo aconteceu através do sistema.
